Every user- and agent-visible string in the three repos, pulled from source rather than hunted by eye, then read back by six reviewers — one per surface, plus one reading all of it as a single voice.

Two audiences share this list. A rail label is read by a buyer choosing a wheel; a tool description is read by a model deciding which call to make. Those get rewritten against different standards, so every row says which it is. Tick a row when you've rewritten it — the marks persist in this browser.

Surfaces

How to read the audience column

Assigned by kind, not by guess. Tool names and tool descriptions are model — nobody sees them but the agent choosing a call. Tool titles, error messages, aria-labels and <meta> tags are both: they surface in the activity log, a screen reader or a link preview as well as to the model. Everything else is person. Where a string does double duty it is marked both rather than split — rewrite it for the harder reader.

Where the replacements came from

Six reviewers read the extracted strings against the project's own standard: never claim more than the app is showing. Their proposed wording is a starting point, not a verdict — the argument under each one is the part worth reading, because it says what the current string does wrong. A handful of findings point at strings the extractor did not capture (markup fragments, a line of README shell); those carry their own file:line and no inventory row.

What this list does not contain

Strings assembled at runtime from parts, text inside the three.js scene drawn as geometry rather than set as a string, and third-party copy. Line numbers are from the working tree on the extraction date and drift the moment you start editing — treat file:line as a pointer, not an address.
